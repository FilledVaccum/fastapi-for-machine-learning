## 1. Project Overview: Patient Management System

The core idea of this project is to develop a **backend API for a doctor's clinic application** that manages patient records. Instead of traditional paper-based prescriptions and records, this system aims to bring the entire process online.

*   **Problem Statement**: Doctors currently maintain patient records on paper, leading to potential misplacement of documents and inefficient retrieval.
*   **Solution**: Provide doctors with an application (via an API) to maintain patient profiles electronically.
*   **Patient Profile Example**: A typical patient profile could include name, city, age, gender, height, weight, and BMI.
*   **Data Storage**: For this basic project, patient records will be stored in a **`patients.json` file**, simulating a database.
*   **API Functionality (CRUD Operations)**: The API will support the following interactions:
    *   **Create**: Add new patient records.
    *   **View/Retrieve**: Fetch all patient records or a specific patient's profile.
    *   **Update**: Modify existing patient records (e.g., change weight, which then auto-adjusts BMI).
    *   **Delete**: Remove patient records.
*   **Our Role**: As backend engineers, our task is to **develop this API** with several endpoints, not the frontend application itself.

## 2. Understanding HTTP Methods (CRUD Operations)

Before diving into API development, it's essential to understand **HTTP Methods**, which are fundamental to how dynamic software and websites interact.

### Static vs. Dynamic Software/Websites

*   **Static Software/Websites**: Primarily used for **receiving information** with minimal user interaction (e.g., a calendar application, a blog website).
*   **Dynamic Software/Websites**: Characterized by **extensive two-way interaction** between the user and the software (e.g., Microsoft Excel, Instagram, Zomato).

### The CRUD Paradigm

For any dynamic software or website, all possible user interactions can be categorized into four fundamental types, collectively known as **CRUD**:

*   **C - Create**: Adding new data or resources (e.g., creating a new Excel sheet, writing a new Instagram post).
*   **R - Retrieve**: Viewing or fetching existing data or resources (e.g., viewing existing Excel cells, scrolling through an Instagram feed).
*   **U - Update**: Modifying existing data or resources (e.g., changing values in Excel, editing an Instagram comment).
*   **D - Delete**: Removing data or resources (e.g., deleting Excel cells, deleting an Instagram post).

### Mapping CRUD to HTTP Methods

When interacting with dynamic websites and APIs over the internet (using the HTTP protocol), specific **HTTP verbs (methods)** are used in the request to tell the server what type of CRUD operation the client wants to perform:

*   **GET**: Used for **Retrieving** information from the server. If you want to view a page or fetch data, you use a GET request.
    *   *Example*: Accessing a course page on a website, viewing all patient records.
*   **POST**: Used for **Creating** new resources or sending data to the server for processing.
    *   *Example*: Submitting a login/registration form, creating a new patient record.
*   **PUT**: Used for **Updating** an existing resource on the server.
    *   *Example*: Updating a user's address, modifying an existing patient record.
*   **DELETE**: Used for **Deleting** a specified resource from the server.
    *   *Example*: Deleting an old address, removing a patient record.

These four are the most commonly used HTTP methods, with GET and POST being more frequent. Our project's API endpoints will utilize these methods to manage patient data.

### Patient Data Storage (`patients.json`)

*   A **`patients.json` file** is created to store the initial patient data. This file will serve as a mock database for this project.
*   The file contains a list of patient records, each being a JSON object.

### Helper Function: `load_data`

To easily read data from `patients.json` repeatedly, a helper function `load_data` is defined:

```python
import json

def load_data():
    """
    Loads all patient data from the 'patients.json' file.
    """
    with open("patients.json", "r") as f:
        data = json.load(f)
    return data
```

### Creating the `GET /view` Endpoint

This endpoint will allow clients to **retrieve all patient records** from our `patients.json` file. Since it's about fetching data, we use the **`GET` HTTP method**.

```python
from fastapi import FastAPI
import json

# Initialize FastAPI app object
app = FastAPI()

# Helper function to load data from JSON (as shown above)
def load_data():
    with open("patients.json", "r") as f:
        data = json.load(f)
    return data

# Modify existing / endpoint
@app.get("/")
def hello():
    return {"message": "Patient Management System API"}

# Modify existing /about endpoint
@app.get("/about")
def about():
    return {"message": "A fully functional API to manage your patients' patient records"}

# Define the new GET /view endpoint
@app.get("/view")
def view_all_patients():
    """
    Retrieves and returns all patient data from the JSON file.
    """
    patients = load_data()
    return patients
```

### Running the API and Accessing Documentation

1.  **Run the Uvicorn Server**: From your terminal (with the virtual environment activated), execute:
    ```bash
    uvicorn main:app --reload
    ```
    *   `main`: Your Python file (`main.py`).
    *   `app`: Your FastAPI application instance.
    *   `--reload`: Automatically reloads the server on code changes.

2.  **Access Endpoints**: Open your browser and navigate to:
    *   `http://127.0.0.1:8000/` (Home endpoint)
    *   `http://127.0.0.1:8000/about` (About endpoint)
    *   `http://127.0.0.1:8000/view` (New endpoint to see all patient data).

3.  **Interactive Documentation**: FastAPI automatically generates interactive API documentation. Visit `http://127.0.0.1:8000/docs` to explore all endpoints, including the new `/view` endpoint. You can **"Try it out"** directly from the documentation to test the API.
